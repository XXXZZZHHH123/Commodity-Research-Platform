## 0. 结论

**取数跑在服务器自己身上**：`tin.jobs daily` 直连各官方源，由 systemd timer 调度
（工作日 08:00 与 16:30，见 `deploy/container/systemd/`）。这条路已经实现，不需要新机制。

**曾经提过一版「GitHub Actions 抓原件 → 提交到 data-raw 分支 → 服务器 git fetch 回放入库」，
已否决。** 否决理由只有一条，但足够致命：**服务器连不上 GitHub**。链路在第三步就断了，
剩下只能靠人工搬运文件，那不叫自动。同样的原因，`ci-deploy.yml` 里的 self-hosted runner
部署路径也走不通，实际交付走的是离线容器包（`docs/OFFLINE_DEPLOYMENT.md`）。

这份文档保留下来，是因为推演过程中量到的东西对现在这条路仍然有用：各源的发布窗口与体量、
三个踩过的坑、以及一个保留下来的工具。

### 0.1 保留了什么

| 保留项 | 为什么还有用 |
|---|---|
| `ingest/raw.py` + `snap-raw` / `import-raw` | 服务器若访问不到境外源（FRED 与 CBOE 占库内观测的绝大多数），在能上网的机器上抓原件、拷进服务器回放入库。走与在线采集完全相同的 `record()` 闸门，`tests/test_raw_replay.py` 断言两者逐行一致 |
| 收盘前的解析修复 | 见 §4.5 第 2 条。08:00 那次 timer 每天都会撞上，不修就是每天一条假失败 |
| FRED 不能带浏览器 UA | 见 §4.5 第 1 条。现有代码恰好躲过，但没写明原因，容易被后人改坏 |
| CI 合规断言 | 校验版本库里没有 `*.db` / `data/`。跑在 GitHub 托管 runner 上，不受服务器出网限制 |

### 0.2 待确认

服务器到底能连到哪些数据源，决定 `snap-raw` / `import-raw` 是常用工具还是可以删掉。在服务器上跑：

```bash
curl -sI --max-time 20 https://www.shfe.com.cn/data/tradedata/future/dailydata/kx20260918.dat | head -1
curl -s  --max-time 20 -o /dev/null -w '%{http_code}\n' https://cdn.cboe.com/api/global/us_indices/daily_prices/VIX_History.csv
curl -s  --max-time 20 -o /dev/null -w '%{http_code}\n' 'https://fred.stlouisfed.org/graph/fredgraph.csv?id=DGS2&cosd=2026-08-01&coed=2026-09-18'
```

全部 200 → 删掉 `raw.py` 及其 CLI 与测试；境外源不通 → 它就是那条搬运通道。

## 1. 被否决方案的推演（存档）

> 以下为 v1.1 的原文，**其结论已被 §0 推翻**，保留是为了记下量到的数据与踩过的坑。

**原方案：GitHub Actions 只负责「按时抓取原件并留证」，不负责入库。**

Actions 每个交易日定时下载各官方源的原始文件，原样提交到仓库的 `data-raw` 分支；服务器执行
`import-raw` 回放这些原件入库。当时给出的三条理由中，前两条今天依然成立，第三条已经落地：

1. **事实库不能上云。** `data/tin.db` 当前 5.1 MB、8574 条观测，其中登记了 6 个 SMM / LME / ICDX 授权源指标，是人工录入通道的落点。把这个库提交到 GitHub，等于把商业授权数据外发给第三方——与 00 §7.1 和导出文件上「内部投研参考 严禁外发」的标注自相矛盾。**这条不因方案否决而失效**，已固化为 CI 的合规断言。
2. **有些数据错过就永久丢失。** 外汇交易中心的中间价接口只返回当日值（`runner._fx` 里显式抛 `NotPublished`），库中至今只有 1 条 CFETS 观测就是证据。**这条现在由服务器上的 timer 承担**——前提是服务器常开且能连上该接口。
3. **回放层几乎不用写新代码。** 现有解析函数本来就是纯函数，`runner.py` 里那几个 `_quotes` / `_warrant` 只是「取 URL + 调解析器」的薄壳。这条已验证成立，也是 `raw.py` 得以保留的原因。

**漏掉的前提**：整套设计假设服务器能从 GitHub 拉取，这一点从未验证，而事实相反。教训是——
涉及网络可达性的设计，可达性本身就是第一个要测的东西，不能默认。

## 3. 候选方案对比（存档）

| | 方案 | 数据落点 | 合规 | 状态冲突 | 结论 |
|---|---|---|---|---|---|
| A | Actions 跑 `daily`，把 `tin.db` 提交回仓库 | 仓库内二进制库 | ✗ 授权数据外发 | ✗ 与本机双写必然分叉，SQLite 无法合并 | **否决** |
| B | **Actions 抓原件留证，本地回放入库** | 仓库 `data-raw` 分支（纯文本原件） | ✓ 仅公开交易所文件 | ✓ 单向：Actions 只写 raw，本机只写 DB | **推荐** |
| C | Actions 只做探活，失败开 issue | 无 | ✓ | ✓ | 不满足「自动取数」，但其告警能力并入 B |
| D | 内网部署 self-hosted runner | 内网 DB | ✓ | ✓ | **二期可选**，需常开内网机 |
| E | Actions 写云端 Postgres（`TIN_DATABASE_URL`） | 云数据库 | ✗ 同 A | ✓ | 否决，与一期内网定位冲突 |

A 之所以最先被否掉，除合规外还有一条硬伤：SQLite 是二进制，git 既做不了有意义的 diff，也无法在两处同时写入后合并——一旦内网和 Actions 都跑过 `daily`，两个库会各自长出不同的修订号，没有任何自动办法把它们合回去。B 把写入权收敛到单向（Actions 只追加 raw 文件、永不改 DB；本机只读 raw、只写 DB），冲突在结构上就不存在。

## 4. 原方案架构（存档；§4.5 的三个坑仍然有效）

### 4.1 职责切分

```
GitHub Actions（境外、常开、不可信存储）
  └── 按时下载原件 → 校验能解析 → 提交到 data-raw 分支
                                        │
                                        │ git fetch
                                        ▼
本机 / 内网服务器（可信、可间歇开机）
  └── import-raw 回放 → record() 闸门 → tin.db → compute → snapshot
      人工录入 SMM/LME 等授权数据（永不出网）
```

Actions 侧**不碰数据库**：`tin.ingest.raw` 这个模块不牵连 `tin.db` 与 `tin.models`（由 `test_snapshot_path_never_touches_the_database` 守住），`snap-raw` 只做 HTTP 下载与落盘。CI 上因此既不需要跑迁移，也不会建出一个空库被误提交。

### 4.2 留证目录结构

提交到 `data-raw` 分支（孤儿分支，不进 `main` 历史，克隆主线时用 `--single-branch` 不受影响）：

```
raw/
├── shfe/quotes/2026-09-18.dat            # 按日不可变：当日原件即证据
├── shfe/warrant/2026-09-18.html
├── shfe/weekly/2026-09-18.html
├── cfets/ccpr/2026-09-18.json
├── cboe/VIX_History.csv                  # 全量历史型：覆盖同一路径，靠 git 历史留版本
├── fred/DGS2.csv                         # 同上，21 个序列
└── manifest/2026-09-18.json              # 当次抓取台账
```

两类文件区别对待的理由：交易所当日件是**不可变证据**，必须按日期分文件；VIX 与 FRED 每次返回的是全量历史（VIX 单次 473 KB），按日存会迅速膨胀且 99% 内容重复，覆盖同一路径让 git 自己做增量 delta 更省。

`manifest/{date}.json` 记录每个源的 `source_url`、HTTP 状态码、`fetched_at`（UTC）、字节数与 `sha256`。这条台账同时服务两个目的：回放时校验文件未被篡改；以及为 P2 的「每个数字都带来源」补上原件级的证据链。

### 4.3 容量估算

每交易日压缩后约 **24.6 KB**（16.3 + 6.8 + 1.5），周五多 16.1 KB。全年 250 个交易日 ≈ **7 MB/年**。VIX 与 FRED 覆盖写入，delta 后每日增量在百 KB 级。

结论：体量不构成问题，无需 Release assets 或外部对象存储，直接用分支即可。若干年后确有需要，`data-raw` 是孤儿分支，可以整枝重建而不影响主线历史。

### 4.4 需要新增的代码

| 新增 | 位置 | 说明 |
|---|---|---|
| `plan_day(d)` | `src/tin/ingest/raw.py` | 声明当天要抓的全部原件：URL、HTTP 方法、落盘路径、是否按日不可变、是否带浏览器 UA。与 `runner.FETCHERS` 共用同一批 URL 常量，并由测试断言两者的源集合完全一致 |
| `snapshot_day(d, out_dir)` | `src/tin/ingest/raw.py` | 下载 + 落盘 + 写 manifest，**不牵连任何 DB 模块**；下载后立即试解析，结构变化当场暴露 |
| `replay_day(session, d, raw_dir)` | `src/tin/ingest/raw.py` | 读原件 → 调现有 `parse_*` 纯函数 → 走 `store()` / `record()` 入库，并照常写 `fetch_runs` |
| `latest_snapshot(raw_dir)` | `src/tin/ingest/raw.py` | 最新台账日期，供页面暴露「定时任务是否还活着」 |
| `cmd_snap_raw` / `cmd_import_raw` | `src/tin/jobs/__main__.py` | 两个 CLI 子命令；`import-raw` 支持 `--days N` 批量回放 |
| 回放一致性测试 | `tests/test_raw_replay.py` | 用现有 fixtures 断言「在线抓取入库」与「原件回放入库」产生完全相同的观测行 |

最后一条测试是这个方案的安全带：只要它绿着，就能保证回放路径不会悄悄偏离在线路径。

**实测结果（2026-09-21）**：抓取 9/18 与 9/21 两天原件耗时 71 秒；回放到真实库的副本上，9/18 的上期所三项**新增 0 行**——这一天的数据当初是在线采集入库的，回放一行不差地重现了它。同一批原件连续回放两次，第二次全部为 0。另外 9/21 的中间价 6.7487 被抓到了，而这个值如果当天没人开机就永久丢失。

### 4.5 实现中撞到的三件事

这三件都是写代码时才暴露的，文档初稿里一条都没料到，记在这里免得下次重蹈：

1. **FRED 不能带浏览器 UA。** 带上常见的 Chrome UA 并发请求时，对方不拒绝也不响应，直接挂到读超时——实测 6 条请求全军覆没，去掉 UA 后 5.5 秒全部成功。现有的 `runner._fred` 恰好用的是不带 header 的 `httpx.get`，无意中躲过了，但那里没写明原因，很容易被后人「顺手统一加上 UA」改坏。现已在两处都加了注释，并有 `test_fred_requests_never_carry_a_browser_ua` 盯着。
2. **收盘前的行情文件是 200，不是 404。** 上期所在收盘前就挂出当日 `kx{date}.dat`，里面有盘中的持仓与成交，但 `CLOSEPRICE`、`SETTLEMENTPRICE` 全是空串，`o_year_num`（年内期号）也还没定。原先这会让解析抛 `ValueError` 并被判成「失败」——意味着每天早盘那次定时取数都会误报一次。现在 `parse_quotes` 对这种文件抛 `NotPublished`，在线路径一并受益；那份不完整的原件也不会被留证。
3. **滚动文件不能套用不可变校验。** VIX 与 FRED 每次返回全量历史、覆盖同一路径，所以后一天的抓取必然改掉前一天台账里记的 sha256。最初对所有文件一律校验，结果回放 9/18 时 FRED 直接报「原件可能已被改动」。现在只对按日期命名的文件做校验，滚动文件的哈希退回为一条线索；解析时按 `through=目标日` 截断，所以拿新文件回放旧日期的结果仍然正确。

### 4.6 三个 workflow

**这三个 workflow 已随方案一并撤销，仓库里不存在。** 下面保留它们的设计要点，万一日后服务器能连上 GitHub 可以直接捡起来。

#### ① `probe.yml` —— 先回答「GitHub 的机器够得着上期所吗」

**整个方案唯一的未知数。** 上期所与外汇交易中心是否对境外 IP 可达、是否有速率或 Referer 限制，本地验证不了，必须在 Actions 上实测。沿用项目既有的「Day-1 探针」做法：手动触发，只打印状态码与首行内容，不写任何数据、不产生提交。FRED 那一条刻意不带 UA（见 §4.5 第 1 条）。

**判读**：`200` 且体量与本地实测同量级（kx 约 120 KB、ccpr 约 11 KB）即通过。若 SHFE / CFETS 返回 403、被重定向到验证页或超时，说明境内源在 Actions 上取不到，按 §7 改走退路，而不是硬撑。

#### ② `fetch-raw.yml` —— 每日取数留证

三个定时时段（UTC，北京时间减 8 小时）：

| cron | 北京时间 | 目的 |
|---|---|---|
| `43 1 * * 1-5` | 09:43 | 中间价发布后。该接口只给当日值，错过永久丢失 |
| `17 9 * * 1-5` | 17:17 | 上期所日行情与仓单发布后 |
| `23 23 * * 0-4` | 07:23（次日） | 美东收盘后的 FRED 与 VIX |

分钟刻意避开整点——那是 GitHub 调度最拥挤的时候。每次运行都额外回补前 3 个自然日，配合 `record()` 的幂等性兜住调度延迟与漏跑。

退出码约定：**全部源成功、或明确「未发布」（节假日、非交易日、尚未收盘）时退出 0**，只有真实故障才非 0。失败时开 issue，已有未关闭的同类 issue 则追加评论，避免连续失败刷屏。权限只给 `contents: write`（提交 `data-raw`）与 `issues: write`。

#### ③ `ci.yml` —— PR 门禁

两个 job：

- `test`：143 个测试全部离线，无需 Secret，单次约 1 分钟。
- `compliance`：校验版本库里不存在 `*.db`、`data/`、`exports/`、`raw/`。合规红线写进 CI 比写进文档可靠——`tin.db` 里有人工录入的授权数据，一旦提交就等于外发。

建议在仓库设置里把这两项设为 `main` 的必需检查，让「未经测试的代码进 main」在机制上不可能。

## 5. GitHub Actions 的四个坑（存档，已不适用）

这四条都会直接影响取数的可靠性，必须在设计里兜住，而不是等出事再查。

### 5.1 定时不准，且可能漏跑

`schedule` 用 UTC，且 GitHub 官方明确说明高峰期会延迟，整点尤其拥挤，极端情况下会**直接跳过某次触发**。

对策有三层：把 cron 分钟设在非整点（上面用了 `:43` `:17` `:23`）；每次运行都额外回补最近 N 天而非只取当天；依赖 `record()` 的幂等性兜底——重复回放同一天的原件不会产生任何多余行。所以「多跑几次」永远是安全的，这正是可以放心用不精确调度的前提。

### 5.2 仓库 60 天无活动，定时任务会被自动停用

GitHub 会在仓库 60 天没有活动后停用所有 `schedule` 触发。更隐蔽的是：**用 `GITHUB_TOKEN` 推送的提交不会被视为能重新触发 workflow 的活动**，所以 bot 自己每天提交 raw 并不必然续命。

对策：把「定时任务是否还活着」变成可观测的——在品种页的数据缺口区读取最新 manifest 的日期，超过 3 个交易日没有新原件就显式报缺口。这与 FR-3.1 已有的缺口机制是同一套展示逻辑，不需要新建告警渠道。若要彻底规避，改用 PAT 推送或外部定时器触发 `repository_dispatch`，但那会引入一个需要轮换的密钥，与当前「零密钥」的优势相冲突，建议一期先不引入。

### 5.3 时区换算

runner 是 UTC，业务时刻全是北京时间。`_date()` 默认取 `datetime.now(SHANGHAI).date()`——这一点现有代码已经做对了，**Actions 上不要设 `TZ` 环境变量去糊弄它**，保持显式时区换算。上表 cron 的换算：北京时间减 8 小时得 UTC；`07:23 北京` 对应前一日 `23:23 UTC`，因此星期字段写 `0-4`（周日到周四）才能覆盖周一到周五的早晨。

### 5.4 节假日不是故障

中国法定假日上期所不发布，URL 直接 404；美国假日 FRED 不更新。现有代码已用 `NotPublished` 区分「未发布」与「失败」，`snap-raw` 必须沿用同一区分，否则十一长假会连开七天 issue，很快没人再看告警。

## 6. 合规审查（对照 00 §7.1，仍然有效）

| 检查项 | 结论 |
|---|---|
| 是否新增订阅源抓取入口 | 否。`SOURCES` 仅含 SHFE / CFETS / CBOE / FRED，与现有 `FETCHERS` 一一对应，不新增任何源 |
| 是否有 SMM / Mysteel / LME / ICDX 的网络请求 | 否。这四家仍然只有人工录入通道 |
| 授权数据是否离开内网 | 否。人工录入值只存在于 `data/tin.db`，而该库被 `.gitignore` 排除，且 Actions 侧不产生也不上传任何 DB 文件 |
| 提交到 GitHub 的是什么 | 仅上期所、外汇交易中心、CBOE、FRED 公开发布的原始文件 |
| 私有仓库 | 是。即便如此，仍应把「不提交 DB」作为硬约束，不依赖仓库私有性做合规兜底 |

**建议加一条 CI 断言**：workflow 里校验 `git diff --cached --name-only` 不含 `*.db`、不含 `data/`，一旦有人误提交事实库立即失败。合规红线写进测试，比写进文档可靠。

## 7. 若 SHFE / CFETS 不可达（退路，仍然有效）

这是唯一可能推翻主方案的分支，预案如下（按优先级）：

1. **拆成境内外两条线**：FRED（21 序列）与 CBOE 留在 Actions——境外源在 GitHub 上的可达性和速度反而优于境内机器（本地实测 FRED 6.1 s、VIX 11.7 s，均偏慢）；SHFE 与 CFETS 回落到本机 cron。这条拆分本身就有独立价值，即便探针全绿也值得考虑。
2. **self-hosted runner**（方案 D）：把 runner 装在内网常开机器上，保留 Actions 的调度与可观测性，数据完全不出网。代价是需要一台常开且能出网连 GitHub 的机器。
3. **仅告警**（方案 C）：Actions 退化为探活，本机 cron 仍是取数主力。

无论走哪条，`import-raw` 回放层都不白写——它同时也是「本机断网期间补数」和「历史回填」的通道。

## 9. 验收清单（其中 2–5 条已在本机验证通过）

1. `probe.yml` 手动触发一次，五个源的状态码与体量与本地实测同量级
2. `snap-raw --days 3` 在本地产出 `raw/` 与 `manifest/`，manifest 中每个源都有 `sha256` 与 `fetched_at`
3. 把 `data/tin.db` 换成空库，执行 `import-raw --days 3`，得到的观测行与在线 `fetch` 逐行一致（由 `tests/test_raw_replay.py` 自动断言）
4. 同一天的原件连续回放两次，第二次新增观测数为 0（幂等）
5. 造一个 404 的日期（周末），`snap-raw` 退出码为 0 且 manifest 标记「未发布」，不开 issue
6. 造一次网络故障（改 URL 为不可达），退出码非 0 并开出 issue
7. 在 PR 中故意让一个测试失败，`ci` 检查变红且无法合并
8. 尝试把 `data/tin.db` 加入提交，CI 合规断言失败
9. `main` 分支的克隆体积不因 `data-raw` 分支显著增长（`git clone --single-branch`）
10. 连续运行两周后，`fetch_runs` 中无因调度延迟导致的永久缺口

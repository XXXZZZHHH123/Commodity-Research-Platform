# 07 · SMM 终端整体导入方案

> 版本 v1.1 ｜ 2026-09-22（v1.1 补网页摘要确认通道） ｜ 上级文档 `PRD/00_总控.md`、`PRD/04_附录_数据字典与设计规范.md`
> 适用范围：SMM 终端导出工作簿（`tin.xlsx`）的整体入库

---

## 1. 为什么另开一条通道

网页批量导入（方案 05）面向研究员手工整理的几十行表格，逐行预览确认。SMM 终端导出的这本工作簿实测 **41.5 万个有效数值点**——不是"再放宽一点上限"就能装下的量，而且装下了也没用：**几十万行没人逐行看得完，实际操作只会是点全选，预览就退化成闭眼信任。**

所以分的不是"大小"，而是**要确认的东西根本不同**：

| | 逐行预览 | 批次确认 |
|---|---|---|
| 面向 | 研究员手工整理的表格 | SMM 终端原样导出的工作簿 |
| 规模 | ≤ 12 万单元格 | 几十万条 |
| 对齐方式 | `[series_id]` 标签 / 名称匹配（**会猜错**） | **SMM 指标Id**（精确，不存在猜错） |
| 要确认什么 | 这一列绑对指标了吗、这个值对吗 | 259 个新指标、跨度 2006–2026、有没有口径冲突 |
| 入口 | `/sn/entry` 上传 | 同一个上传框（自动识别）或 `python -m tin.jobs import-smm` |

**逐行预览存在的唯一理由是"表头靠名字猜、可能猜错"。** 终端导出按稳定编码对齐，这个不确定性不存在，逐行确认也就无从确认起。两条通道最终都汇入同一个 `record()` 闸门，没有第二条写入路径。

## 2. 这本工作簿长什么样

每张表是「日期 × 指标」的宽表，前四行固定：

```
R1 指标名称   SHFE: 锡: 主力合约: 收盘价: 日度
R2 指标Id     a10024116        ← 供应商稳定编码
R3 单位       元/吨
R4 频率       日
R5+ 数据      首列日期，其余为数值
```

**指标Id 是这条通道的地基。** 它稳定、唯一、与显示名无关——SMM 改了名称的写法也不会错位。这恰好填上了网页通道的痛处：那边 87 个列因为「`SMM1#锡_均价(元/吨)`」对不上「`SMM 1# 锡现货均价`」而全军覆没，而 `indicators` 表本来就有 `vendor_code` 字段，一直没被用起来。

实测（2026-09-22 的 `tin.xlsx`）：

| | |
|---|---|
| 工作表 | 14 张，其中 13 张符合格式，1 张空表跳过 |
| 序列 | 280 列 → 去掉 4 个重复 Id → **276 条** |
| 其中标注「（停）」 | 16 条，不导入 |
| 有效数值点 | **415,532**，实际入库 398,348（去掉停用列） |
| 时间跨度 | 2006-01 ~ 2026-09 |
| 来源构成 | SHFE 148 · SMM 89 · LME 27 |

## 3. 设计决定

### 3.1 series_id 用 `SMM.<指标Id>`，不猜名字

276 条序列，逐个起可读的 id 需要人工定名 276 次，而且必然有歧义（30 多个分仓库名怎么转写？）。改用供应商编码：

- `SMM.a10024116` — 稳定、唯一、可重复导入不漂移
- 可读性由 `name` 字段承担，存 SMM 的完整层级名（`SHFE: 锡: 主力合约: 收盘价: 日度`），信息量比任何自造短名都大

**已登记的指标走 `OVERRIDES` 映射，不另建一份。** 目前只有一条：`s20002960 → SMM.SN.spot.1`（BASIS 的现货端）。研究员日后要把某条序列提升为「正式指标」，往这张表里加一行即可，历史数据自动归到新 id 下。

### 3.2 口径能推的推，推不出的留空

从 SMM 的层级命名里可以确定地推出：

| 维度 | 依据 |
|---|---|
| `time_type` | SHFE / LME 的行情与仓单是交易时点；SMM 自采的报价、调研、平衡表是发布时点 |
| `price_type` | 名称含结算价 / 收盘价 / 平均价 / 开盘价 / 最高价 / 最低价 |
| `contract_kind` | 主力合约 / 连二合约 |
| `stock_scope` | 仓单 → 交易所注册仓单；社会库存 → 社会库存；其余库存 → 交易所库存 |
| `weight_basis` | 单位就是金属吨 / 实物吨 |
| `spot_source` | 仅限现货价序列：1#锡 → SMM，长江 1#锡 → 长江有色 |

**推不出的一律留空，不猜。** 口径字典是同时点守卫的唯一依据——填一个猜的值比留空危险得多，守卫会拿它去判「两端是否同口径」，猜错就放行了本该阻断的计算。典型例子：个旧市场不在 `SpotSource` 枚举里，于是 `spot_source` 留空并在 `note` 里写明原因，而不是塞一个字典外的字符串。

### 3.3 时刻补齐要留痕

日期单元格只有日期没有时刻，按发布方的常规发布时刻补齐（SHFE 15:00、LME 19:00、SMM 11:30），并在每条观测的 `note` 里写明「时刻按 XX 常规发布时刻补齐」。系统不替人编造时点，但补齐规则必须显式可查。

### 3.4 口径字典扩了两处

这次导入迫使口径字典（04 §3）增补，都是追加，不影响已有数据：

- `PriceType` 增加 **开盘价 / 最高价 / 最低价**。不加的话这些列只能留空口径，而守卫会把两个空口径当成同类放行——开盘价配最高价算价差不会被拦。
- `ContractKind` 增加 **连二连续**。SMM 的连二合约是数据商拼接的次近月连续序列，与主力连续不可混算。

### 3.5 `record()` 加了批量缓存参数

39.8 万条逐条 SELECT 会让入库从分钟级变成小时级。但闸门只能有一个，所以做法是**把预取的最新值索引喂给 `record()`**，而不是另开一条绕过校验的写入路径。校验、判重、修订号逻辑一字未改，`test_batch_cache_behaves_exactly_like_the_uncached_gate` 逐项断言两种调用方式行为一致。

实测：首次导入 2 分 55 秒，重复导入 1 分 19 秒（写入 0，全部识别为值未变）。

## 4. 用法

```bash
# 先试算，只统计不入库
python -m tin.jobs import-smm /path/to/tin.xlsx --by 张三 --dry-run

# 确认后入库
python -m tin.jobs import-smm /path/to/tin.xlsx --by 张三
```

重复执行安全：同 `series_id + as_of` 值不变则跳过，值变了追加修订号保留历史。SMM 修订历史数据时，再跑一次即可，改动会作为新修订留痕。

## 4.1 网页通道：摘要确认 + 后台任务

命令行解决了"能不能导入"，但研究员想做的是**把文件直接拖进网页**。做法不是放宽单元格上限——那会让一条为不确定性设计的路去跑一个没有不确定性的文件。

**判断的层级要跟着数据规模走。** 逐行预览存在的理由是"这一列到底绑哪个指标"：表头靠名字猜，猜错会静默写脏数据，所以要人逐行核。SMM 终端导出按指标Id 精确对齐，这个不确定性根本不存在——几十万行里人唯一能做的动作就是点全选，预览只剩成本。

所以网页上传时先探测格式，命中就切到摘要确认：

```
POST /api/sn/import/preview
  ├─ 非终端格式 → 原有逐行预览（≤ 12 万单元格）
  └─ 终端格式   → 暂存文件 + 返回批次摘要
                  POST /api/sn/import/smm/commit  → 立刻返回 job_id
                  GET  /api/sn/import/jobs/{id}   → 前端每 2 秒轮询进度
```

确认页给的是人判断得了的东西：

| | |
|---|---|
| 新登记指标 | 259 个（按分类展开：库存与流通 118 · 价格 95 · 其他 17 · 情绪 15 · 矿端 8 · 供需平衡 4 · 需求 2） |
| 复用已登记 | 1 个（SMM 1# 锡现货均价 — SMM.SN.spot.1） |
| 跳过已停用列 | 16 列 |
| 观测点 | 398,348 条 |
| 时间范围 | 2006-01-01 ~ 2026-09-22 |
| 口径冲突预检 | 0 条 |

**口径冲突提前预检。** 冲突只可能出在已登记的那几条上，所以在摘要阶段就逐条核一遍，不用等跑了三分钟才发现。

### 几个实现上的取舍

- **暂存文件落盘，不入库。** `import_previews.payload` 的设计约定是"只存入库所需的最小集合，不保留整表副本"，塞一个 3.4 MB 的 xlsx 进去就破坏了这条。改为写 `settings.staging_dir`（部署时软链到持久卷），任务跑完即删，过期的由 `purge()` 清理。
- **令牌只允许 uuid4 的 32 位 hex**，正则校验后才拼路径，杜绝路径穿越；任务状态返回给前端时剔除令牌。
- **任务状态放进程内存。** 一期是单进程 uvicorn，够用。进程重启会丢失进行中的任务，但 `record()` 幂等，重跑一次即可，不会写重。
- **后台执行走 FastAPI `BackgroundTasks`。** 端点是同步 `def`，FastAPI 在线程池里跑，不阻塞事件循环。

## 5. 实测结果

**命令行**（真实库的副本）：

```
指标 新登记 259 / 复用 1 / 跳过停用 16；观测 写入 398,348 / 值未变跳过 0 / 拒绝 0
再跑一次：写入 0 / 值未变跳过 398,348
```

**网页通道**（同一份副本，完整走一遍上传 → 摘要 → 确认 → 轮询）：

```
上传 3.4 MB 工作簿 → 摘要返回      2.6 秒
确认导入          → 立刻返回 job_id
轮询进度          7% → 15% → 46% → 69% → 100%
最终 done 100%   新登记 259  写入 397,171  值未变 1,177  拒绝 0
暂存文件已自动删除，审计日志已写入
```

值未变的 1,177 条正是此前用整理版 Excel 导进去的现货价——同一条序列走两条通道，第二次被正确识别为"值未变"，没有重复写入。

库体积 5 MB → 265 MB。SQLite 仍可承受，但这个量级已经接近一期「单机 SQLite」的合理上限；再扩两个品种就该考虑 PostgreSQL 了（`TIN_DATABASE_URL` 已支持，无需改码）。

导入过程中闸门拦下过一条：`SMM.SN.spot.1 口径不符：登记为 spot_source=SMM，本次入库为 spot_source=None`——推导逻辑当时漏了现货来源。这正是 P2 该拦的，补上推导后重跑即零拒绝。**闸门拦住了我的实现错误，这比任何测试都说明它有用。**

## 6. 已知限制

1. **场次维度缺失。** SMM 有「夜盘收盘价」「10点15收盘价」「收盘价(10:30)」「收盘价(15:00)」等同一价格类型的不同场次，口径字典里没有对应维度，目前都归为 `price_type=收盘价`，场次信息只落在 `note`。跨场次比价的守卫暂时拦不住。要补的话需要在 04 §3 增加一个 `session` 维度，属于口径字典的结构性变更，应由研究员决定。
2. **与自动采集的重叠未做交叉校验。** SMM 转载的 SHFE 主力收盘价（`SMM.a10024116`）与我们直连上期所取的 `SHFE.SN.main.close` 是两条独立序列，数字可能有差异（SMM 的「主力合约」定义未必与我们按持仓量选出的一致）。两者互不覆盖，但也还没有任何地方把它们并排比对。做一个一致性报表是自然的下一步。
3. **判断需要的指标只覆盖了一部分。** 这本工作簿含现货均价、社会库存（SMM 口径）、LME 库存、缅甸矿进口；**云南 40% TC、焊料开工率、ICDX 成交量不在其中**，仍需另行取得。
4. **社会库存的口径分歧未解。** 文件里是 SMM 口径，证伪条件 `fl_social_stock_2w` 绑的是 Mysteel 口径的 `MYSTEEL.SN.stock.social`。本次导入把 SMM 的存为 `SMM.a10020744`，两者并存互不干扰，但证伪条件到底该读哪一条，需要研究员拍板。

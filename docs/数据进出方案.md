## 0. 一张表看清全部通道

数据进入事实层只有四条路，出去只有两条。**所有写入都汇入同一个闸门 `tin.ingest.record.record()`，没有第二条写入路径。**

### 进

| # | 通道 | 面向 | 规模 | 对齐方式 | 确认方式 | 入口 |
|---|---|---|---|---|---|---|
| 1 | **自动采集** | 交易所与公开源 | 每日几十条 | 代码内声明 | 无需确认 | `jobs daily`（systemd timer 工作日 08:00 / 16:30） |
| 2 | **单条人工录入** | 临时补一个数 | 1 条 | 下拉选指标 | 表单即确认 | `/sn/entry` |
| 3 | **Excel 批量导入** | 研究员手工整理的表格 | ≤ 12 万单元格 | `[series_id]` 标签 / 名称匹配（**会猜错**） | **逐行预览** | `/sn/entry` 上传 |
| 4 | **数据商终端整体导入** | SMM / 钢联原样导出 | 几十万条 | **供应商编码**（精确，不会猜错） | **批次摘要** | 同一个上传框（自动识别）或 `jobs import-terminal` |
|   | ↳ 新编码 | 库里没见过的编码 | — | — | 自动登记新指标 | 同上，无需改码 |
| 4b | 离线原件搬运 | 服务器直连不到的源 | 不限 | 同自动采集 | 台账 sha256 校验 | `jobs snap-raw` → 拷贝 → `jobs import-raw` |

### 出

| 通道 | 面向 | 入口 |
|---|---|---|
| **自定义导出 Excel** | 研究员按需组合列 | `/sn` 的「自定义导出 Excel」抽屉 |
| JSON 快照 / 合约 CSV | agent 读取、归档 | `/api/sn/snapshot`、`/sn/contracts.csv` |

### 为什么 3 和 4 不能合并

**逐行预览存在的唯一理由是「表头靠名字猜、可能猜错」。** 猜错会静默写脏数据，所以要人逐行核。

数据商终端导出按稳定编码对齐，这个不确定性根本不存在——几十万行里人唯一能做的动作就是点全选，预览只剩成本、没有安全收益。所以分的不是"大小"，而是**要确认的东西根本不同**：通道 3 确认"这一列绑对指标了吗"，通道 4 确认"要不要新增 259 个指标、跨度对不对、有没有口径分歧"。

## 1. 不变量（所有通道共同遵守）

1. **事实层闸门不妥协（P2 / P3）**：所有写入必须经过 `record()`，强制绑定 `series_id`、`as_of`、`caliber`、`source`；口径冲突或未登记指标严禁落库。
2. **严禁人工导入篡改自动采集指标**：只有 `fetch_mode == 'manual'` 的指标可被人工写入。交易所行情、汇率中间价、VIX 一律拒绝。
3. **严禁系统替人编造时点**：日期单元格无时刻时按指标登记的发布时刻补齐，但必须在预览中显式展示、允许整列微调，并在入库 `note` 中永久留痕。
4. **不出数保护（FR-5.2）**：派生计算处于 `blocked` 时导出必须留空并附批注，严禁输出看似正常的数值或静默空白。
5. **禁止前向填充**：周频、月频指标在日频宽表中非发布日必须留空，绝不沿用前值。
6. **商业数据合规（00 §7.1 / 04 §8）**：SMM、Mysteel、LME 的订阅数据零抓取代码；带出系统必须带合规警示并写审计日志。
7. **服务端权威校验**：确认入库只认服务端暂存的 `preview_id` / `job token`，前端不能回传裸数据绕过校验。
8. **确定性状态机**：无隐式记忆，模板微调显式标记 `[已修改]`。

## 2. 通道 3：Excel 批量导入（逐行预览）

代码：`src/tin/ingest/excel_importer.py`

### 2.1 防绕过架构

上传 → 服务端解析校验 → 暂存 `import_previews`（TTL 30 分钟）→ 返回 `preview_id` 与四类清单 → 用户勾选 → commit 只认 `preview_id`。

`import_previews.payload` **只存入库所需的最小集合**，不保留原始单元格全文或整表副本。清理是双重的：每次新建预览时删过期行，`jobs daily` 再扫一次。

### 2.2 对齐规则

- **优先级 1 — 显式代码**：表头含 `[SMM.SN.spot.1]` 则正则提取直接绑定。精确绑定，**不触发任何变体警告**，保证"系统导出的文件原样导回"100% 无损。
- **优先级 2 — 名称匹配**：仅在无代码标签时启用，且受品位防呆约束。

**品位防呆**：若名称匹配到的指标口径含 `tc_grade / weight_basis / stock_scope / spot_source / import_code / contract_kind` 任一维度，一律要求人工确认——库里可能只登记了 40% TC，而表里那列正是没登记的 60%。

**数量级异常**：与该指标近期中位数相差一个数量级时给出 `WARN_MAGNITUDE_OUTLIER` 警告（不阻断）。

### 2.3 四类清单

| 类别 | 含义 | 默认勾选 |
|---|---|---|
| 可导入 | 新数据 | ✓ |
| 将产生修订 | 同 `series_id + as_of` 已有不同值 | ✗ 需逐条确认 |
| 相同忽略 | 值完全一致 | — 自动跳过 |
| 异常未导入 | 非数值、未登记、自动采集指标、时点不可解析 | ✗ 不可选 |

**逐行通道不会自动登记指标。** 表头写着库里没有的 `[series_id]` 或名称，一律归入异常并说明原因（`表头代码 X 未在指标登记表中找到` / `系统未登记该指标`），绝不静默造一个指标出来——这条通道面向的是人手工整理的表格，表头拼错的概率远高于"真有一个新指标"。要引入新指标走通道 4，或先在指标页登记。

### 2.4 提交阶段的二次校验

- **并发陈旧拦截**：预览与确认之间库内被写入不同数值，该行归入 `stale_rows` 并拒绝覆盖，不悄悄改写。
- **改绑重校验**：`column_overrides` 改绑的列必须重新校验指标存在、可用、为人工录入类。
- **多日重算**：导入 N 个交易日的数据后，逐日触发 `compute_day`，返回 `recalculated_dates`。

### 2.5 规模上限：12 万单元格

实测预览耗时与规模严格线性，约 **0.105 秒/千单元格**、payload 约 **165 KB/千单元格**：

| 单元格 | 预览耗时 | payload | 预览行数 | 浏览器插入 DOM |
|---|---|---|---|---|
| 5 万（原上限） | 5.4 s | 8 MB | 4 万 | 250 ms |
| **12 万（现上限）** | **12.6 s** | **20 MB** | 9.6 万 | ~480 ms |
| 15 万 | 15.8 s | 25 MB | 12 万 | ~600 ms |
| 41.5 万 | 44 s | 69 MB | 33 万 | 1.1 s |

约束按硬度排序：**① 15 秒验收线**（对应约 14 万）→ **② payload 存进 `import_previews` 单行** → **③ 人还确认得过来吗**。

浏览器不是瓶颈——实测 33 万行插入 DOM 只要 1.1 秒、JS 堆 381 MB。真正不该再往上抬的理由是 ③；更大的文件走通道 4。

## 3. 通道 4：数据商终端整体导入（批次确认）

代码：`src/tin/ingest/vendor_terminal.py`、`src/tin/ingest/import_jobs.py`

### 3.1 两家的版式：不同，但同类

| | SMM | 钢联 Mysteel |
|---|---|---|
| 横幅行 | 无 | `钢联数据` |
| 元数据行 | 指标名称 / **指标Id** / 单位 / 频率 | 指标名称 / 单位 / **指标编码** / 频度 / 指标描述 / 更新时间 |
| 表头行数 | 固定 4 行 | **不固定**（Sheet1 少「更新时间」一行） |
| 缺失标记 | 空、`-` | 空、`-`、**`#N/A`** |
| 编码样例 | `a10024116`、`s20002960` | `ID01538256`、`FU00082529`、`CM0000138665` |

差异都是表层的，结构是同一类：**若干行元数据在上、日期索引的数据在下，且都给了稳定的供应商编码**。所以读取器只有一份（99 行），各家差异收在一个 `Vendor` 声明里。

**表头行数不固定**决定了不能按行号取数据：数据起点靠「首列是日期」判断。认不出版式的工作表整张跳过，不猜。

### 3.2 series_id 与 OVERRIDES

新序列一律 `<前缀>.<供应商编码>`（`SMM.a10024116`、`MYSTEEL.ID01538259`）。可读性由 `name` 字段承担，存供应商的完整层级名。

**已登记的走 `OVERRIDES` 映射，不另建一份。** 现有 4 条：

| 编码 | 归入 | 判断里的角色 |
|---|---|---|
| `s20002960` | `SMM.SN.spot.1` | BASIS 的现货端 |
| `ID01538256` | `MYSTEEL.SN.TC.YN40` | 多头证据 bull1 |
| `ID01517441` | `MYSTEEL.SN.stock.social` | **证伪条件 `fl_social_stock_2w`** |
| `FU00082529` | `ICDX.SN.volume` | 白名单 |

**编码归属的优先级**（`resolve_ids`）：

1. **库里的 `vendor_code` 绑定** —— 研究员把编码登记到某个可读 series_id 上，导入就归到那里
2. 代码里的 `OVERRIDES` —— 只是尚未登记时的引导
3. 都没有 → 自动登记新指标 `<前缀>.<编码>`，并把编码写进 `vendor_code`（下次第 1 条就命中，自我强化）

**库优先是必须的**：只查 `OVERRIDES` 的话，研究员在库里做完绑定后导入仍会另建一个 `SMM.<编码>`，同一条序列**无声裂成两个**。人在库里做的绑定是权威的。同一编码被登记到多个指标时不替人选，在摘要页报 `code_conflicts` 让人先合并。

**往 `OVERRIDES` 加一条的门槛**：只有当那个编码**已经登记在 `indicators.vendor_code` 里**（即有人做过这个绑定）时才可以直接加；否则属于新的判断，应由研究员决定，不由实现者代劳。

### 3.3 口径怎么定

**已登记指标以登记口径与登记发布时刻为准**，不用按名称推导的那个。

钢联的「锡锭：库存：中国（周）」按名称会被推成交易所库存，而它登记的是社会库存——推导若参与校验，这条本该入库的数据会被闸门挡住，挡的还是推导自己的错。人按编码做的绑定比按名称的推导权威；单条人工录入读的也是 `ind.caliber`，这里保持一致。

**未登记的才推导**，能确定的才填：

| 维度 | 依据 |
|---|---|
| `time_type` | 交易所行情与仓单是交易时点；数据商自采的报价、调研、平衡表是发布时点 |
| `price_type` | 名称含结算价 / 收盘价 / 均价 / 开盘价 / 最高价 / 最低价 |
| `contract_kind` | 主力合约 / 连二合约 / 连续合约 |
| `stock_scope` | 仓单 → 交易所注册仓单；社会库存与数据商自采锡锭库存 → 社会库存；LME 期货库存 → 交易所库存 |
| `weight_basis` | 单位就是金属吨 / 实物吨 |
| `spot_source` | 仅限现货价序列：1#锡 → SMM，长江 1#锡 → 长江有色 |
| `tc_grade` | 名称含 `40%Sn` / `60%Sn` |

**推不出的一律留空，不猜。** 口径字典是同时点守卫的唯一依据——填一个猜的值比留空危险得多，守卫会拿它判「两端是否同口径」，猜错就放行了本该阻断的计算。典型例子：个旧市场不在 `SpotSource` 枚举里，于是留空并在 `note` 写明原因。

**但差异要说出来。** 登记口径与推导口径不一致时，摘要页逐条列出「`price_type` 登记为 X，按名称推导为 Y」，以登记为准但让人看见——两者打架只说明推导规则有问题，或者那条登记绑错了编码。频率不符同样列出。

### 3.4 网页通道：摘要确认 + 后台任务

```
POST /api/sn/import/preview
  ├─ 非终端格式 → 逐行预览（≤ 12 万单元格）
  └─ 终端格式   → 暂存文件 + 返回批次摘要
                  POST /api/sn/import/terminal/commit → 立刻返回 job_id
                  GET  /api/sn/import/jobs/{id}       → 前端每 2 秒轮询进度
```

确认页给的是人判断得了的东西：新登记指标数（按分类展开）、复用已登记、跳过停用列、观测点数、时间范围、**其中晚于今天的点**、登记与推导的差异、频率不符。

实现上的取舍：

- **暂存文件落盘，不入库**。`import_previews.payload` 约定不保留整表副本，塞 3.4 MB 的 xlsx 进去就破坏了这条。改写 `settings.staging_dir`（部署时软链到持久卷），跑完即删。
- **令牌只允许 uuid4 的 32 位 hex**，正则校验后才拼路径，杜绝路径穿越；任务状态返回前端时剔除令牌。
- **任务状态放进程内存**。一期单进程 uvicorn 够用；重启会丢进行中的任务，但 `record()` 幂等，重跑不会写重。
- **`record()` 的批量缓存参数**：几十万条逐条 SELECT 会让入库从分钟级变小时级，所以把预取的最新值索引喂给闸门，而不是另开一条绕过校验的路。校验、判重、修订号逻辑一字未改，有测试逐项断言两种调用行为一致。

### 3.5 实测

| | SMM `tin.xlsx` | 钢联 `tin_mysteel.xlsx` |
|---|---|---|
| 工作表 | 14 张（13 张可解析） | 5 张（全部可解析） |
| 序列 | 276 条（去重后），16 条停用不导 | 97 条，无停用 |
| 观测点 | 398,348 | 131,810 |
| 时间跨度 | 2006-01 ~ 2026-09 | 1990-01 ~ 2026-12 |
| 新登记 / 复用 | 259 / 1 | 94 / 3 |
| 命令行耗时 | 2 分 55 秒 | 14.6 秒 |
| 重复导入 | 写入 0，识别 398,348 条值未变 | 同左 |
| 拒绝 | 0 | 0 |

网页通道端到端：上传 3.4 MB → 摘要 2.6 秒 → 确认立刻返回 job_id → 轮询 7%→100% → 暂存自动删除、审计已写。

**闸门在实测中拦下过一条**：`SMM.SN.spot.1 口径不符：登记为 spot_source=SMM，本次入库为 spot_source=None`——推导逻辑漏了现货来源。补上后重跑零拒绝。闸门拦住的是实现者自己的错误，这比任何测试都说明它有用。

## 4. 通道 4b：离线原件搬运

代码：`src/tin/ingest/raw.py`

服务器若访问不到某些源（尤其境外的 FRED、CBOE），在能上网的机器上 `jobs snap-raw` 下载官方源原件并写台账（`source_url`、HTTP 状态、`fetched_at`、字节数、`sha256`），把 `raw/` 目录拷进服务器再 `jobs import-raw` 回放。

回放走与在线采集**完全相同的 `parse_*` 与 `record()`**，`tests/test_raw_replay.py` 断言两条路径产生逐行一致的观测。实测回放 9/18 的原件到真实库副本上新增 0 行——那天的数据当初是在线采集入库的，回放一行不差地重现了它。

**不可变与滚动两类文件区别对待**：交易所当日件按日期分文件、sha256 参与校验；VIX 与 FRED 每次返回全量历史、覆盖同一路径，哈希只作线索不参与校验（否则回放旧日期必然失败），解析时按 `through=目标日` 截断保证等价。

### 采集中踩过的三个坑（仍然有效）

1. **FRED 不能带浏览器 UA**。带 Chrome UA 并发请求时对方不拒绝也不响应，直接挂到读超时——实测 6 条全军覆没，去掉后 5.5 秒全部成功。现有 `runner._fred` 恰好用的是不带 header 的 `httpx.get`，无意中躲过，已补注释与回归测试，免得被"顺手统一加上 UA"改坏。
2. **上期所收盘前返回 200 而不是 404**。文件已挂出但收盘价是空串、`o_year_num` 未定。原先解析抛 `ValueError` 被判成「失败」，意味着每天早盘那次定时取数都会误报。现在 `parse_quotes` 抛 `NotPublished`，在线路径一并受益。
3. **滚动文件不能套用不可变校验**（见上）。

## 5. 导出

代码：`src/tin/export/excel.py`、`src/tin/export/templates.py`

### 5.1 排版与往返无损

- **第 1 行即表头**，表头写成 `指标名称 [series_id]`，导出的文件原样导回识别率 100%、变体警告 0。合规警示放说明页与打印页眉，不放第 1 行——放了就破坏机器可读性。
- 冻结首行首列；第 2 个 Sheet 是数据字典（口径、单位、来源、**本区间数据覆盖**）。
- **指标停用或删除时优雅降级**：模板里引用了已停用指标，导出照常进行，该列留空并在响应头 `X-Export-Skipped` 说明，不整份失败。

### 5.2 出数保护：五类批注

| 情形 | 单元格 | 批注 |
|---|---|---|
| 派生被阻断 | 留空 | `[阻断不出数: 口径/时点不一致]` |
| 缺少输入 | 留空 | `[缺少输入] …` |
| 尚未计算 | 留空 | `[未计算] 该交易日尚未执行派生计算` |
| 观测缺失 | 留空 | `[数据缺失] 预期更新时点: {expected_by}` |
| 低频指标的非发布日 | 留空 | `[非发布日]` |

**批注按序列的实际覆盖区间判断**：区间外（该序列尚未开始）的空白不再逐格标注，改由字典页的「本区间数据覆盖」列统一说明。否则导出五年时，一个今年才登记的指标会有上千条无信息量的批注。

### 5.3 数据区间

30 / 90 / 180 个交易日、1 年、2 年、5 年、自定义。旧模板里的 60 / 120 键仍然解析，不会失效。选固定区间时起止日期输入框不出现。

### 5.4 模板

同品种只允许一个默认模板（部分唯一索引兜底）。默认模板可删，删后自动把剩余模板中 `updated_at` 最新的一个顶上；删光则回到未命名配置空态——避免「默认模板永远删不掉」的死角。

### 5.5 合规

导出含商业授权数据时，说明页与打印页眉标注「内部投研参考 严禁外发」，并写 `audit_log`。研判类字段导出必须带过期标记。

## 8. 量化验收

- **导出性能**：500 交易日 × 20 列（含批注与字典页）≤ 2.0 秒
- **导入性能（常规）**：5,000 单元格返回 `preview_id` ≤ 3.0 秒
- **导入性能（上限）**：120,000 单元格 ≤ 15.0 秒，解析期间前端进度动画不得静默
- **多日重算**：一次导入 60 个交易日，60 天 `compute_day` 总耗时 ≤ 3.0 秒
- **规模硬上限**：超过 120,000 单元格拦截并提示分批；识别为终端格式则改走通道 4，不受此限
- **幂等性**：同一份已入库文件再次上传，100% 归入「相同忽略」，写入与修订严格为 0
- **往返无损**：系统导出的文件原样导回，识别匹配率 100%，多品位警告 0
- **并发防陈旧**：preview 与 commit 间隙插入新值，commit 能识别冲突行并归入 `stale_rows`
- **闸门安全**：非法或过期 `preview_id` / `token` 返回 400/404，无法绕过

### 9.2 导出抽屉

颜色不表达多空。阻断与异常用 `--alert`，警告与「需确认」用 `--amber`，主操作用 `--primary`。

## 10. 未来：API 接入

结论先行：**这套结构绝大部分用得上，有些部分会变得更重要。**

`vendor_terminal.py` 528 行里，真正绑死在 Excel 上的只有 **99 行**（`read_workbook` / `_header_of` / `detect`）。

### 作废的

那 99 行。取代它的是一个十几行的薄壳——跟 `runner.py` 里 `_quotes` / `_fred` 一样：发请求、解析 JSON、吐出 `Series` 列表。**下游一行不用改**，因为 `Series` 这个中间结构不关心数据从哪来。

### 原样保留的

| 部分 | 为什么 API 也要 |
|---|---|
| `record()` 闸门 | API 写入照样要过：指标登记、停用、口径一致、值未变跳过、变了追加修订。**API 更需要它**——人工导入至少有人在看，自动同步没人看 |
| `indicators.vendor_code` | 变得更有用：API 返回就是按供应商编码索引的，这个字段正是对到我们 `series_id` 的桥；现有 `OVERRIDES` 直接复用 |
| 口径推导层 | **API 不解决口径问题**。它给 name / unit / frequency / code，但不会告诉你这条是 40% 还是 60% 品位、是社会库存还是交易所库存。规则一模一样 |
| 修订机制 | 价值更高：数据商会回溯修订历史，现在靠重导才发现；每日同步则当天捕获并留痕 |
| `import_jobs` 后台任务 | API 首次回补同样几十万条、几分钟，一样要后台跑、要进度、要审计 |
| 批次摘要确认 | **更需要**：一次同步若要新登记 259 个指标，人还是该看一眼再确认，而不是让它自己长 |
| `runner.py` 采集框架 | 失败重试一次、`NotPublished` 区分未发布与故障、`fetch_runs` 台账、单源失败不中断其余——本来就是为 API 设计的模式，新数据商就是往 `FETCHERS` 加一个 `Fetcher` |

### 会变的一件事，是好事

导入进来的指标现在 `fetch_mode` 都是 `manual`。转 API 后应改为 `auto`，于是 `record()` 里现成的守卫自动生效：**同一条序列一旦转为自动采集，人工就再也覆盖不了它**。

### 需要新做的

**增量同步**。现在是"整本重读、靠幂等去重"（41 万条 3 分钟）；API 应改成"只取上次 `as_of` 之后的"。逻辑很薄。

### 一句话

Excel 导入是临时的，事实层的结构不是。这套东西真正的产出不是"能读 xlsx"，而是三样：**`record()` 这道唯一闸门、`vendor_code` 这座桥、口径推导 + 人工登记覆盖的那套约定**。反过来说也成立——现在图省事直接灌库、不过闸门、不定口径，等 API 来了这些债一分不少还在，而且到时候没人逐行看了，只会更难发现。

## 11. 已知边界

1. **场次维度缺失。** SMM 有「夜盘收盘价」「10点15收盘价」「收盘价(10:30)」等同一价格类型的不同场次，口径字典没有对应维度，目前都归为 `price_type=收盘价`，场次只落在 `note`。跨场次比价的守卫拦不住。补的话需在 04 §3 加 `session` 维度，属字典的结构性变更。
2. **与自动采集的重叠未做交叉校验。** SMM 转载的 SHFE 主力收盘价与我们直连上期所取的是两条独立序列，数字可能有差异（SMM 的「主力合约」定义未必与我们按持仓量选出的一致）。互不覆盖，但还没有地方并排比对。
3. **判断绑定的 8 个指标仍差 2 个。** 现已有数据：主力结算价、VIX、TC、社会库存、LME 库存、ICDX 成交量。仍为 0 条的两个：
   - `CUSTOMS.2609.import.MM`（缅甸锡矿进口）—— 钢联**无**分国别数据（「关别」是海关关区不是来源国）；SMM 有自采口径的缅甸矿进口量，但与登记的海关口径未必一致。**海关总署有公开月度数据，该写采集器而不是买**。
   - `SMM.SN.solder.oprate`（焊料开工率）—— 两家导出里都没有。钢联只有「锡：冶炼厂：开工率」（`ID02226391`），那是冶炼端供给，与焊料端需求方向相反，**不可映射**。SMM 终端应有此序列（登记的 `a10083975` 就是 SMM 编码），下次导出勾上即可自动归位，无需改码。
4. **社会库存两家并存。** SMM 的存为 `SMM.a10020744`，钢联的归入 `MYSTEEL.SN.stock.social`（证伪条件绑的就是它）。口径不同、互不干扰，但并排比对能看出分歧多大——值得做，还没做。
5. **年频/季频按期末标注会产生未来日期的点**（2026 年均值标在 12-31，而这年没走完）。不拦（拦了会丢掉所有历史年度数据），摘要页报出条数。
6. **库体积**。两本工作簿全导入后库约 265 MB。SQLite 仍可承受，但已接近一期「单机 SQLite」的合理上限；再扩两个品种就该上 PostgreSQL（`TIN_DATABASE_URL` 已支持，无需改码）。

## 13. 决策记录

### 13.1 GitHub Actions 取数方案（已否决，2026-09-21）

曾设计「Actions 抓原件 → 提交到 `data-raw` 分支 → 服务器 `git fetch` 回放入库」。**否决理由只有一条但足够致命：服务器连不上 GitHub**，链路在第三步就断，剩下只能人工搬运。取数继续走 `jobs daily` + systemd timer，跑在服务器自己身上。

推演中仍然成立的三条：① 事实库不能上云（库里有人工录入的授权数据，提交到 GitHub 等于外发，已固化为 CI 的合规断言）；② 中间价接口只给当日值，错过永久丢失；③ 解析函数都是纯函数，从文件回放与从网络抓取可以共用同一条入库通道——这条是 §4 那个搬运工具得以保留的原因。

**教训**：涉及网络可达性的设计，可达性本身就是第一个要测的东西，不能默认。

### 13.2 上限从 5 万提到 12 万（2026-09-22）

原 5 万是拍的，理由写成"性能保护"，而实测 5 万只要 5.4 秒。按 15 秒验收线反推上限约 14 万，取 12 万留余量。同时明确：**真正的约束不是性能而是"人还确认得过来吗"**，所以更大的文件换通道而不是继续抬上限。

### 13.3 已登记指标以登记口径为准（2026-09-22）

原先无论是否已登记都用名称推导的口径，导致钢联「锡锭：库存：中国」被推成交易所库存而与登记的社会库存冲突，本该入库的数据被闸门挡住。改为已登记者以登记为准，但把差异摆在摘要页——**以登记为准不等于静默**。
